How much RAM does a small web app really need

Picking a server size feels like a guessing game until you've burned money on a $40/month box that sits at 4% CPU while your $6/month droplet gets OOM-killed at 3am. Let's cut through the uncertainty with real numbers so you can make a confident choice before you deploy—and know when it's time to scale up.

Start With What's Actually in Memory

RAM usage for a web app isn't just your application code. The real number is a sum of several layers running simultaneously:

  • Operating system baseline – Ubuntu 22.04 LTS idles at roughly 180–250 MB on a fresh VPS
  • Your runtime – Node.js starts around 30–60 MB per process; a Python/gunicorn worker is 40–80 MB; a Go binary can sit under 15 MB
  • Your web server – Nginx typically uses 5–15 MB total; Caddy is similar
  • Database – If SQLite, near zero extra cost; PostgreSQL with default settings uses 20–30 MB at idle but climbs fast under load
  • Background workers, cron jobs, monitoring agents – easily another 50–100 MB you forgot to account for

Add it up and a realistic "simple" stack is already at 400–600 MB before a single user hits the front page.

Real-World Benchmarks by Stack

Node.js + Express + SQLite

A straightforward REST API with a few routes and no heavy dependencies idles around 80–120 MB. Spin up four workers with PM2 and you're looking at 350–450 MB steady-state. This stack runs comfortably on a 1 GB droplet for a few hundred concurrent users, with room left for the OS and Nginx.

Python + Django or FastAPI + PostgreSQL

Django with 4 gunicorn workers hits roughly 400–600 MB depending on installed apps. FastAPI is leaner—3 uvicorn workers land closer to 200–300 MB. If PostgreSQL lives on the same server, add another 50–150 MB depending on shared_buffers config. A 1 GB VPS is tight here; 2 GB gives you breathing room.

Ruby on Rails + Puma

Rails is the RAM-hungry one. A stock app with 3 Puma threads can consume 300–500 MB on its own. Factor in PostgreSQL and you're pushing against a 1 GB limit quickly. Budget for 2 GB minimum if you want stable deployments.

Go or Rust microservice

These are outliers in the best way. A compiled Go API serving JSON typically uses 15–40 MB at rest. You can run multiple services plus Postgres on a 512 MB server and still have headroom. If you're choosing a runtime and RAM cost matters, this is worth noting.

A Simple Sizing Formula

Use this rough calculation before you order your next server:

Required RAM =
  OS baseline (~250 MB)
  + (workers × per-worker memory)
  + database idle footprint
  + buffer for spikes (20–30%)
  + any sidecar processes

For a Django app with 4 gunicorn workers and local Postgres, that's roughly: 250 + (4 × 120) + 100 + 130 = ~960 MB. That's why a 1 GB server is risky—you want 2 GB.

What Happens When You Under-Provision

The Linux OOM killer isn't subtle. When your server runs out of RAM it starts terminating processes—usually the most memory-hungry one, which is typically your app server. You wake up to a dead site, no log entry explaining why, and a confused database that didn't get a clean shutdown. Enable swap as a safety net, but don't rely on it for performance—swapping to disk can make a web server 10–20x slower under load.

Adding 1 GB of swap on a DigitalOcean or Hetzner VPS takes two minutes and has saved countless indie apps from 3am incidents:

fallocate -l 1G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

Cost vs. Headroom: The Practical Tiers

  • 512 MB (~$4–5/mo) – Only viable for compiled languages (Go, Rust) or very simple PHP sites. Add swap immediately.
  • 1 GB (~$6–8/mo) – Good for Node or lightweight Python apps. Keep the database elsewhere or use SQLite.
  • 2 GB (~$12–18/mo) – The sweet spot for most indie apps. Handles Django, Rails, or Node with a local Postgres comfortably.
  • 4 GB (~$24–36/mo) – Ready for moderate traffic, multiple workers, and some caching layers. Most small teams won't need to go beyond this until they have real revenue.

Before You Upgrade, Profile First

If your server is struggling, check actual consumption before throwing money at it. SSH in and run:

free -h
ps aux --sort=-%mem | head -15

Often you'll find a rogue background job, an untuned shared_buffers in Postgres, or a memory leak in one worker that's the actual culprit. Fixing the root cause is cheaper than the next server tier—and you'll understand your stack better for it.

The honest answer to how much RAM you need is: more than the minimum spec, less than you think once you measure it properly. Start with 2 GB for anything Python or Ruby, 1 GB for lean Node or Go apps, always add swap, and actually monitor memory in production for the first week. You'll stop guessing and start knowing.
